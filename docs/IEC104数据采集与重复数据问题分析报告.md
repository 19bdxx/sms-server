# IEC104 数据采集链路与重复数据问题分析报告

> 分析日期：2026-05-07  
> 分析人员：Copilot 代码审查  
> 代码仓库：sms-server（IEC 60870-5-104 数据采集与处理工程）

---

## 1. 分析背景

### 业务背景

科创园平台中发现部分场站/风机数据存在**长时间连续重复值**，尤其江苏 2024 年 9 月到 12 月的数据几乎全部重复。真实风机的有功功率、无功功率、风速、风向、运行状态在任何时间段都不可能完全不变，因此存在以下几种可能：

1. 平台在没有收到新数据时，使用上一条数据进行填充；
2. IEC104 总召唤时，对端返回的是同一份旧快照，平台每轮给它打上新的本机时间戳并入库；
3. 采集监听层维护了缓存，未收到新值时仍然用缓存值生成新记录；
4. 日志回放/历史补录逻辑读取旧日志或重复日志，导致重复入库；
5. 数据组合或标准化处理时，某些缺失字段被上一条数据、默认值或缓存值补齐；
6. 入库前没有做值变化判断、质量位判断、源端时间判断，导致旧值持续保存成新数据。

### 本次分析目标

通过逐文件分析代码，确认上述哪种情况实际存在于代码中，并给出具体文件路径、类名、方法名和代码逻辑依据。

```java
    if (getConnection() != null) {
```

### 3.3 定时任务配置

**文件路径** → `src/main/java/com/powcal/task/BrokerTask.java`  
**类名** → `BrokerTask`

```java

@Scheduled(cron = "${monitor.cron2}")  // cron2: 23 * * * * ?
```

`application.yml` 配置：
```yaml

  cron1: 3 * * * * ?
  cron2: 23 * * * * ?
  cron3: 45 * * * * ?
```

**每分钟触发 3 次总召唤**（在第 3 秒、第 23 秒、第 45 秒）。但 `acceptData()` 内有一个去重检查：

```java
// BrokerTask.java:39-56
private void acceptData() {
    LocalDateTime time = LocalDateTimeUtil.now().withSecond(0);  // 截断到分钟
    // 查询 POWCAL_SITEPOW 表是否已存在当前分钟数据
    QueryWrapper<PowcalSitepowEntity> queryWrapper = new QueryWrapper();
    queryWrapper.lambda().eq(PowcalSitepowEntity::getHappenTime, localDateTime);
    List<PowcalSitepowEntity> powcalSitepowEntities = powcalSitepowService.list(queryWrapper);
    if (powcalSitepowEntities.size() > 0) {
        return;  // 已有数据则跳过
    }
    J60870Connection.Interrogation();  // 否则触发总召唤
}
```

**潜在风险**：第 3 秒触发一次总召唤，总召唤尚未完成（数据尚未入库）时，第 23 秒又触发检查，发现 POWCAL_SITEPOW 表还没有数据，会再次发起总召唤，导致同一分钟内同一份快照数据被保存两次。

### 3.4 总召唤各阶段处理

**文件路径** → `src/main/java/com/powcal/broker104/J60870ClientListener.java`  
**类名** → `J60870ClientListener`  
**方法名** → `newASdu()`

```java
// J60870ClientListener.java:42-53
if (asduTypeId == 100 && cotId == 7) {        // 总召唤激活确认
    STATUS100 = true;
    now = LocalDateTime.now().withSecond(0).withNano(0);  // ⚠️ 使用本机时间

```

### 3.5 ASDU 类型处理范围

**代码仅处理以下两种类型：**

| ASDU 类型 | 含义 | 是否带时标 |
|-----------|------|-----------|
| `type=1` | 单点遥信（Single-point information） | **否** |
| `type=13` | 短浮点遥测（Measured value, short floating point value） | **否** |

**以下带 CP56Time2a 时标的 ASDU 类型完全未处理：**

| ASDU 类型 | 含义 |
|-----------|------|
| `type=30` | 带时标的单点遥信 |
| `type=31` | 带时标的双点遥信 |
| `type=34` | 带时标的归一化遥测 |
| `type=35` | 带时标的标度化遥测 |
| `type=36` | 带时标的短浮点遥测 |

**结论**：代码只处理不含源端时标的 ASDU，因此无法获取数据在源端实际发生的时间。

### 3.6 ⚠️ createTime/happenTime 是本机时间

这是最关键的问题之一。`now` 在收到总召唤激活确认时被赋值：

```java
// J60870ClientListener.java:45（关键问题代码）
now = LocalDateTime.now().withSecond(0).withNano(0);
```

随后，所有在该轮总召唤中收到的点位数据全部使用这个 `now` 作为 `createTime`：

```java
// J60870ClientListener.java:64
doc.setCreateTime(now);
```

**后续入库时直接使用 `createTime` 作为 `happenTime`：**

```java
// JsPowcalFjpowComposeHandler.java:54
powcalFjpowEntity.setHappen_time(monitorRecordDoc.getCreateTime());
```

**这意味着：即使对端每次总召返回的是完全相同的 IOA+value 快照，平台也会用新的本机时间戳将其保存为一条新数据。**

### 3.7 不区分主动总召数据与变化上送数据

代码通过 `STATUS100` 标志位过滤：当 `STATUS100 == true`（总召唤激活确认到总召唤结束之间）时，才处理收到的遥测/遥信数据。**变化上送数据（自发上送，COT=3）在 `STATUS100 == false` 时会被完全忽略。**

```java
// J60870ClientListener.java:55
if (STATUS100 && asduTypeId != 100) {
    // 只处理总召唤期间的数据，变化上送在 STATUS100=false 时会被丢弃
}
```

- 文件名：`data20240901.log.zip`（按日滚动，以 zip 压缩存储）

### 4.3 日志行格式

每行格式为：
```
<now>,<asduTypeId>,<ioa>,<value>
```

示例：
```
2024-09-01T00:03:00,13,1001,1234.5
2024-09-01T00:03:00,1,2001,1
```

**注意**：日志中的时间（第一列）是**本机时间**（`J60870ClientListener.now`），即总召唤激活确认收到时的 `LocalDateTime.now()` 截断到分钟。**不是源端报文时间，也不是数据实际发生时间。**

### 4.4 ⚠️ 日志中同一 IOA+value 可能被多次写入

由于每次总召唤的 `now` 都是新的本机时间，如果对端每次返回相同的值，日志中会出现：

```
2024-09-01T00:03:00,13,1001,125.0
2024-09-01T00:23:00,13,1001,125.0    ← 同一 IOA，同一 value，但时间不同
2024-09-01T00:45:00,13,1001,125.0    ← 同上
```

这说明**日志本身就可能记录了重复值**，并且后续补录会原样入库。

### 5.4 ⚠️ 补录前先删除已有数据

```java
// DataPlusService.java:396-414（dataPlus_manyDay 方法）

    // 先删除当日所有数据
    powcalSitepowMapper.delete(sitepowWrapper);   // DELETE POWCAL_SITEPOW

```

先删后插，如果日志本身就包含重复值，则重复值会被原样入库。

### 5.5 补录无去重逻辑

`dataPlus_GD()` 中调用的 `savePowcalFjpow()` 等方法，只在**同一批次的内存 Map** 中做合并（`Collectors.toMap` 的 merge function），但对于**不同时间戳的同值记录**不做任何过滤。如果日志中同一 IOA 在不同时间（如 00:03、00:23、00:45）都有相同值，则三条记录都会被入库。

## 6. 数据清洗、分拣和标准化逻辑分析

### 6.1 BusHandler / GdBusHandler / JSBusHandler 作用

**GdBusHandler**（广东）和 **JSBusHandler**（江苏）的逻辑几乎完全相同，均按以下步骤分拣数据：

1. 查询 `monitoringPoint` 映射表（通过 `DataPlusService.getMonitoringPoint(capDate)`）；
2. 遍历 `docList`，按 `doc.getMonitoringPoint()` 查找对应映射；
3. 根据 `DEVICE_TYPE` 分流到四个列表：
   - `SYZ` → `powcalSitepowList`（场站升压站功率）
   - `FJ` → `powcalFjpowList`（风机功率）
   - 测风塔 SPEED/DIRECTION 相关 → `powcalCftwindList`
   - PRESSURE/HUMIDITY/TEMPERATURE → `powcalSitetherpowList`

**⚠️ 关键问题**：使用的是**前一天日期**作为映射查询日期：

```java
// GdBusHandler.java:38 / JSBusHandler.java:39
LocalDate capDate = J60870ClientListener.now.toLocalDate().plusDays(-1);
```

这意味着如果点表在近期变更，当天新增或修改的点位将无法正确映射，导致数据丢失。

### 6.2 风机组合 Handler（FjpowComposeHandler）

以 `JsPowcalFjpowComposeHandler.savePowcalFjpow()` 为代表：

```java
// JsPowcalFjpowComposeHandler.java:42-91
Map<String, PowcalFjpowEntity> PowcalFjpowTempMap = pendingList.stream()
    .collect(Collectors.toMap(
        // key = siteId:fanCode:createTime
        doc -> doc.getSiteid() + ":" + doc.getFan_code() + ":" + doc.getCreateTime(),
        // value = 新建实体，按 pointType 设置对应字段
        doc -> { ... },
        // merge = 同 key 时合并，非 null 字段覆盖
        (existing, newData) -> { if (newData.getActivePower() != null) existing.setActivePower(...); ... }
    ));
powcalFjpowService.saveBatch(new ArrayList<>(PowcalFjpowTempMap.values()));
```

- **合并依据**：`siteId + fanCode + createTime`（其中 `createTime` 是本机时间）
- **如果某个点位缺失**：该字段在 Entity 中为 `null`，不会用上一条数据补充（merge function 中只有 `!= null` 才覆盖），即**留空**
- **没有跨批次或跨时间的值填充**：merge 仅在同一 `Collectors.toMap` 操作的内存 Map 中生效

**⚠️ 但存在另一种"重复"风险**：如果同一风机同一时间有多条记录（例如同一分钟被 cron1 和 cron2 各触发一次总召唤），`saveBatch` 会向数据库插入两条 `happenTime` 相同的记录。

### 6.3 缺失数据处理方式

代码中未发现 `lastValue`、`previousValue`、`lastMap`、`oldValue`、`getLast` 等**显式"上一值补充"逻辑**。若某个点位在总召唤中未被返回，则：

- 该点位对应的 Entity 字段为 `null`
- 仍然会调用 `saveBatch` 将含 null 字段的 Entity 入库

## 7. 入库逻辑分析

### 7.1 最终保存的表和实体

| 数据表 | 实体类 | Service |
|--------|--------|---------|
| `POWCAL_SITEPOW` | `PowcalSitepowEntity` | `PowcalSitepowService` |
| `POWCAL_FJPOW` | `PowcalFjpowEntity` | `PowcalFjpowService` |
| `POWCAL_CFTWIND` | `PowcalCftwindEntity` | `PowcalCftwindService` |
| `POWCAL_SITHERPOW` | `PowcalSitetherEntity` | `PowcalSitetherService` |

### 7.2 ⚠️ saveBatch 前无去重

所有 `saveBatch` 调用前均无值变化检查，也无唯一键冲突处理：

```java
// GdPowcalFjpowComposeHandler.java:92
powcalFjpowService.saveBatch(new ArrayList<>(PowcalFjpowTempMap.values()));
```

内存中的 `PowcalFjpowTempMap` 仅对**同一批次内**的同 key 记录做合并，不与数据库中已有数据比较。

### 7.3 无唯一键约束

在 `PowcalFjpowEntity` 和 `PowcalSitepowEntity` 的实体注解中，**未发现唯一键约束（`@TableField` 中无 `unique`，`@TableName` 中无特殊约束注解）**：

```java
// PowcalFjpowEntity.java:19
@TableName(value = "POWCAL_FJPOW")
public class PowcalFjpowEntity extends AbstractEntity {
    @TableId(value = "POWCAL_FJPOWID", type = IdType.INPUT)
    private Integer POWCAL_FJPOWID;
    // 无 siteId+fanCode+happenTime 的唯一约束
}
```

**结论：如果同一 siteId + fanCode + happenTime 被多次插入，数据库会接受并存入多条记录，无任何报错或去重。**

### 7.4 无值变化判断

入库前无任何逻辑检查当前值是否与上一条记录相同（无 `SELECT` 对比，无内存缓存对比），因此每次总召唤结束后，只要流程正常运行，**必然会产生一批新记录入库**，无论对端数据是否有变化。

### 8.1 质量位

```java
// J60870ClientListener.java:113-118
if (id == 1) {
    boolean value = ((IeSinglePointWithQuality) informationElement[0]).isOn();
    map.put("VALUE", value);  // 只取 isOn()，不取质量描述符
} else if (id == 13) {
    float value = ((IeShortFloat) informationElement[0]).getValue();
    map.put("VALUE", value);  // 只取 getValue()，不取质量描述符
}
```

**代码完全不读取 IEC104 质量描述符（QDS）**：

- `IeSinglePointWithQuality` 除 `isOn()` 外还有 `isBlocked()`、`isSubstituted()`、`isNotTopical()`、`isInvalid()` 等方法，均未调用
- `IeShortFloat` 同样有质量字节，未读取

即使对端标记某个点位为"无效（invalid）"、"替代值（substituted）"或"不更新（not topical）"，代码也会将其当作正常数据处理并入库。

### 8.2 时标（CP56Time2a）

代码中**完全不处理** `type=30/31/34/35/36` 等带 `CP56Time2a` 时标的 ASDU 类型。`J60870MonitorRecordEntity` 中只有一个时间字段 `createTime`，其含义为**本机接收时间（批次时间）**：

```java

@JsonFormat(pattern = DatePattern.NORM_DATETIME_PATTERN)
private LocalDateTime createTime;  // 实际含义：本机时间/批次时间
```

入库实体中的时间字段含义：

| 实体 | 时间字段 | 实际含义 |
|------|----------|----------|
| `PowcalFjpowEntity` | `happen_time` | 本机批次时间（由 `LocalDateTime.now()` 生成） |
| `PowcalSitepowEntity` | `happenTime` | 同上 |
| `PowcalCftwindEntity` | `happen_time` | 同上 |
| `PowcalSitetherEntity` | `happen_time` | 同上 |

**数据库中没有 `sourceTime`（源端时间）、`receiveTime`（接收时间）、`batchTime`（批次时间）的区分，只有一个 `happen_time` 字段，实际代表本机批次时间。**

## 9. 重复数据问题结论

### 9.1 是否存在显式"缺失数据使用上一条数据填充"的逻辑？

**结论：不存在。** 代码中未发现 `lastValue`、`previousValue`、`lastMap`、`oldValue`、`getLast`、`order by happen_time desc limit 1` 等任何上一值填充模式。如果某点位未返回，对应字段为 `null`。

### 9.2 ⚠️ 是否存在"总召当前快照 + 本机时间戳入库"导致旧值表现为新数据的机制？

**结论：存在，且是最核心的问题。**

证据链：

```
J60870ClientListener.java:45
    now = LocalDateTime.now().withSecond(0).withNano(0);  ← 本机时间

J60870ClientListener.java:64,79
    doc.setCreateTime(now);  ← 批次内所有点位使用同一本机时间

JsPowcalFjpowComposeHandler.java:54
    powcalFjpowEntity.setHappen_time(monitorRecordDoc.getCreateTime());  ← 直接入库

powcalFjpowService.saveBatch(...)  ← 无值变化判断，无唯一键约束
```

**如果南瑞对端在 2024 年 9 月至 12 月返回的是一批冻结不变的 IOA+value 快照，平台每次总召唤（每分钟最多 3 次）都会将相同的值打上新的本机时间戳存入数据库，产生大量重复记录。**

### 9.3 重复数据最可能发生在哪一层？

按可能性从高到低排序：

1. **104 采集监听层（最高可能）**  
   `J60870ClientListener.newASdu()` 使用本机时间，无值变化检查，每轮总召唤必然插入一批新数据。

2. **入库层（配合上层）**  
   `saveBatch` 无唯一键约束，不拒绝重复数据。

3. **历史补录层（如果曾执行补录）**  
   `dataPlus_manyDay()` 会先删除数据再从日志重新插入，如果日志本身已包含重复值（由于本机时间不同而被视为不同记录），则补录会将所有重复记录原样入库。

4. **南瑞 104 转发侧（外部因素）**  
   如果南瑞 RTU 在 104 采集层的数据本身未刷新（总召唤返回的是缓存快照），则所有后续层面都会受到影响。

### 9.4 关键证据文件和方法

| 文件 | 类 | 方法 | 问题 |
|------|----|------|------|
| `broker104/J60870ClientListener.java` | `J60870ClientListener` | `newASdu()` | 使用本机时间 `LocalDateTime.now()` 作为数据时间，无质量位检查，无值变化检查 |
| `task/BrokerTask.java` | `BrokerTask` | `acceptData()` | 每分钟最多 3 次总召唤，仅靠查询 SITEPOW 表去重，存在竞态导致重复触发 |
| `handler/standardization/*/JsPowcalFjpowComposeHandler.java` | `JsPowcalFjpowComposeHandler` | `savePowcalFjpow()` | 直接 `saveBatch`，无唯一键约束，无值变化判断 |
| `service/DataPlusService.java` | `DataPlusService` | `dataPlus_manyDay()` | 补录先删后插，日志重复值原样入库 |

### 9.5 江苏 2024 年 9 月至 12 月重复数据，应优先查什么？

**建议优先检查原始日志文件**（`/home/powcal/logs/sms/data/data202409*.log.zip`），判断在日志层面是否已存在重复。具体验证方法见第 10 节。

### 9.6 如何判断问题在哪一层

| 现象 | 结论 |
|------|------|
| 日志中同一 IOA 在不同时间有相同 value | 问题在采集层或南瑞侧（不是补录层） |
| 日志中不重复但业务表重复 | 问题在补录层、标准化层或入库层 |
| 南瑞后台画面有变化但 104 日志不变化 | 问题在南瑞对外 104 转发区（点表映射或冻结） |
| 日志中时间连续但 value 完全不变 | 强烈提示总召快照冻结 + 本机时间戳入库 |

### 11.7 修复同一分钟重复触发总召唤的竞态问题

**文件路径** → `task/BrokerTask.java`  
**方法名** → `acceptData()`

当前去重逻辑只查 `POWCAL_SITEPOW` 表，但在第 3 秒触发总召唤完成入库之前（假设需要 20 秒），第 23 秒的检查发现表中还没有数据，会再次触发总召唤。

建议改用分布式锁或 `AtomicBoolean` 状态位：

```java
// 建议增加
private static final AtomicBoolean interrogating = new AtomicBoolean(false);

private void acceptData() {
    if (interrogating.compareAndSet(false, true)) {
        try {
            // 原有逻辑
            J60870Connection.Interrogation();
        } finally {
            // 总召唤结束后（DataCleaning()完成后）释放
            interrogating.set(false);
        }
    } else {
        log.info("上一次总召唤尚未完成，跳过本次触发");
    }
}
```

### 11.8 对日志补录增加重复校验

在 `DataPlusService.dataPlus_GD()` 的 `savePowcalFjpow()` 中，入库前先查询同 `siteId+fanCode+happenTime` 的记录是否已存在，若存在则跳过或更新而非插入。
